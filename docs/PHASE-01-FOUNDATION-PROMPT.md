# NASA Virtual Simulation — Phase 01 Master Implementation Prompt

You are the lead engineer responsible for the first production-grade foundation of the project `NASA-Virtual-simulation` for the NASA Space Apps Challenge 2026 challenge “Abandoned but Not Forgotten: Storytelling about NASA’s Discarded Equipment on the Moon and Mars.” The repository is intentionally empty at the start of this phase, so do not assume that a framework, package manager, UI system, renderer, authentication layer, or directory structure already exists. Your responsibility in Phase 01 is to bootstrap a professional foundation for the much larger 3D educational planetary simulation that will be built over the following phases. This must not become a disposable prototype. Every decision made now must support a future application in which a user enters their name and email, begins on Earth, explores a cinematic 3D solar-system environment containing the Sun, Earth, Moon, and Mars, controls a first-person astronaut, travels between worlds through cinematic transitions, discovers NASA hardware left on the Moon and Mars, opens educational information, follows historical stories, and eventually interacts with artifacts using inspect, pick-up, rotate, and place-back mechanics. The future NASA artifact dataset will be supplied later, so Phase 01 must create the application architecture and contracts that allow those features to be added without rewriting the core.

Because the repository is empty, first choose and bootstrap a modern, production-suitable web stack centered on TypeScript and a React-based application with a structure that can render real-time WebGL. Prefer Next.js App Router with TypeScript for the application shell, React Three Fiber and Three.js for the 3D rendering layer, Drei for carefully selected helpers, and Zustand or an equally lightweight typed state solution for simulation/player/session state. Use a physics library only when it is genuinely needed by later phases; do not add a heavy physics dependency merely because this is a simulation project. Use the latest stable mutually compatible package versions available when implementing, but do not hard-code unnecessary version assumptions into the architecture. Keep the dependency graph intentional and small. The project must be able to run locally with a standard install-and-start workflow and must be deployable to a normal modern web hosting environment without requiring a proprietary local engine. The application must use strict TypeScript configuration and should avoid `any` except at explicitly justified external-library boundaries. Configure linting and formatting consistently. Preserve a clear distinction between server-side application concerns and client-only WebGL concerns, because browser-only APIs, WebGL contexts, pointer locking, device motion, audio contexts, and Three.js rendering must never accidentally execute during server rendering.

Establish the project as a modular simulation platform rather than a collection of pages. Create a clear separation between the application shell, simulation engine, world definitions, world runtime state, player, camera, interaction system, UI overlays, data models, transitions, visual effects, audio management, authentication/session state, utilities, and asset loading. The directory organization should make the conceptual architecture immediately obvious. A structure similar to `src/app` for routes and application layout, `src/components` for reusable UI, `src/simulation` for the Three.js/React Three Fiber runtime, `src/worlds` for Earth/Moon/Mars/Sun world definitions and world-specific configuration, `src/player` for character movement/camera/input logic, `src/ui` for simulation overlays and educational panels, `src/systems` for interaction, transitions, simulation clock, audio and other cross-cutting runtime systems, `src/data` for typed content schemas and seed configuration, `src/assets` for static references and asset registries, `src/services` for persistence and future backend integrations, and `src/lib` for general utilities is strongly preferred. Do not create empty folders merely for appearance; each foundational folder should either contain a minimal useful module, an explicit index, or a documented extension point.

Build a data-driven domain model now. Define typed interfaces or schemas representing at minimum a celestial body, world configuration, world environment configuration, player configuration, mission, NASA artifact, artifact interaction capabilities, educational fact, story segment, media asset, and mission timeline event. A future artifact record must be able to identify a unique artifact ID, display name, mission, celestial body, status, historical importance, coordinate or placement information, visual asset reference, available interactions, scientific contribution, and narrative content without requiring the renderer to know the specific artifact in advance. Do not put future NASA facts into hard-coded rendering logic. Separate content from presentation so the same artifact data can later feed an in-world marker, an info panel, a timeline, a story mode, and eventually a pick-up interaction. Do not invent NASA artifact facts in Phase 01; use clearly marked development-safe sample entities only where needed to validate rendering, and never present placeholder data as official NASA information.

Establish a persistent user session abstraction using only name and email as the initial identity fields. This is not a full password authentication system in Phase 01. The architecture should expose a typed session interface and a service abstraction so local browser persistence can later be replaced by a real backend without rewriting the UI or simulation. Validate name and email on the client, prevent malformed session state from crashing the app, and keep identity state separate from simulation state. Do not expose secrets, API keys, credentials, or server-only environment variables to the client bundle. Create a safe environment-variable strategy and a clear example environment file containing only non-secret placeholders when needed.

Create the application shell with a deliberately minimal visual identity that already points toward a premium scientific simulation. The initial experience should not look like a SaaS dashboard, admin panel, generic template, or gaming HUD. Use a deep-space visual language with restrained typography, strong hierarchy, subtle glass surfaces where appropriate, controlled motion, and a sense of scale. The Phase 01 UI does not need the final cinematic experience yet, but it must establish the visual foundation. Include a root layout, global styles, responsive viewport configuration, a controlled loading state, a basic application entry state, and an explicit simulation mount point. The main screen should contain a real WebGL-capable simulation container, even if the initial scene is intentionally simple. The first scene can use a starfield, a central Sun-like emissive body, Earth, Moon, and Mars placeholders rendered with procedural or lightweight materials, but the architecture must treat these as real world entities rather than decorative background elements. Rotation and orbital movement may remain intentionally basic in this phase, but the simulation loop must be real and frame-independent. Do not fake the simulation with a video, canvas screenshot, or pre-rendered animation.

Create a dedicated simulation runtime that owns the render canvas and separates rendering from application UI. Use a stable client-only boundary for the WebGL scene. The runtime should expose a typed world context or equivalent mechanism so future phases can activate worlds and systems without rebuilding the entire canvas. The renderer should have safe defaults for antialiasing, color management, pixel ratio, camera, lighting, and resize handling. Keep device pixel ratio capped to a performance-conscious maximum rather than blindly using unlimited native DPR. Provide a single source of truth for simulation time and delta time so future orbit calculations, animation systems, and player movement remain frame-rate independent. Make the simulation clock pausable and resettable through a typed API even if only a minimal implementation is exposed in the UI today. Do not put simulation timing into React state on every animation frame; use an imperative runtime or store design that avoids unnecessary React rerenders.

Create the first world/entity abstraction. Earth, Moon, Mars, and Sun should each have an identity and configuration rather than being anonymous mesh objects inside one component. The world model should be able to specify visual properties, transform defaults, environment settings, gravity values for later use, interaction metadata, and a world ID. The Earth, Moon, and Mars entities can initially use high-quality procedural materials or carefully chosen low-weight placeholders, but the API must accept future textures, normal maps, roughness maps, HDR lighting, detailed terrain, cloud layers, atmospheric shells, and mission-specific assets. The Sun should support an emissive visual model and future bloom/post-processing integration. Do not attempt literal astronomical scale inside the scene because that will make interaction and precision impractical; establish a documented simulation scale strategy so visual scale can remain coherent while astronomical relationships can still be described educationally in the information layer.

Build a clean asset-management strategy from the beginning. Static public files should have predictable paths and naming. Avoid scattering asset URLs throughout components. Create an asset registry or typed constants layer where appropriate so future 3D models, textures, sounds, photos, and NASA reference material can be mapped to stable identifiers. The loader architecture should support lazy loading later, because the final project will contain multiple worlds and potentially many artifact models. Do not import every future asset into the first bundle. Establish conventions for optimized texture dimensions, compressed model formats where supported, and graceful missing-asset behavior. A missing non-critical visual asset should not crash the entire simulation; instead, the system should fall back to a recognizable development placeholder and report a useful diagnostic.

Create a lightweight application state model with separate domains for session, current world, simulation clock, player state, camera state, interaction target, UI state, loading state, and transition state. Do not create one giant global object that every component mutates. Use typed actions or methods that make state transitions explicit. The future project will require Earth to Moon travel, Moon to orbit, Mars exploration, target highlighting, info panels, cinematic travel, player movement, artifact interactions, and story mode, so state contracts must already be capable of representing these concepts without being tightly coupled to any specific UI component. Keep transient animation internals in the rendering/runtime layer when appropriate and keep durable application state in the central store.

Create a proper interaction contract now even though Phase 01 will not yet implement the full target/reticle system. The interaction system must be capable of representing an interactive target ID, target type, available actions, distance, interaction availability, and optional metadata. Actions should be generalized to verbs such as ENTER, INSPECT, INFO, SCAN, PICK_UP, PLACE, and RETURN so future objects can declare exactly what they support. The renderer should not decide business logic for these actions. This contract will later allow the central reticle to identify the Moon, a planet, a mission site, or a NASA artifact and choose the correct interaction. Keep line-of-sight, raycasting, distance checks, and action resolution behind an interaction service or system boundary.

Create a transition system abstraction now. Future travel from Earth to Moon or Earth to Mars must not be a simple route change or teleport. The application will eventually perform cinematic camera movement, environment changes, asset loading, and destination activation. Define a typed transition request containing source world, destination world, transition type, optional target location, duration profile, loading requirements, and lifecycle state. Implement only the minimal lifecycle and a safe development transition in Phase 01. The goal is to prevent later phases from hard-coding navigation logic directly into buttons or mesh click handlers.

Establish error boundaries and runtime diagnostics. WebGL initialization can fail, assets can be missing, and browsers can have limited capabilities. The application must not white-screen without explanation. Add a user-friendly fallback for unsupported or failed WebGL contexts, with a clear way to recover or retry. Log developer diagnostics in a controlled way without exposing sensitive information. Avoid permanent noisy console output in normal operation. Create a clear distinction between expected recoverable errors, developer warnings, and fatal initialization failures. Do not hide real errors by swallowing exceptions silently.

Make the foundation responsive even though the final first-person controls will arrive later. The simulation container must resize correctly and respect desktop, tablet, and mobile screen dimensions. Do not assume a fixed 1920x1080 canvas. Prepare the UI layer for future touch controls, virtual analog input, and mobile interaction without implementing a fake mobile layout now. Ensure the initial page has safe-area awareness and does not overflow horizontally. The viewport and canvas should use the available space correctly, and UI overlays should remain pointer-event aware so future interaction controls do not accidentally block WebGL input.

Add foundational accessibility and reduced-motion support. The future experience will contain cinematic movement and visual effects, but users should have the ability to request reduced motion. Respect the prefers-reduced-motion media query in the application shell and animation utilities. Ensure text remains readable over the simulation and that non-3D controls have semantic labels. Do not attempt to make the WebGL world itself fully screen-reader accessible; instead, keep critical educational information and interaction alternatives available in standard DOM UI as the later phases add them.

Create a development and contribution contract. The root README must explain the purpose of the project, current Phase 01 scope, how to install dependencies, how to run development mode, how to build for production, how to lint/type-check, the high-level architecture, and the next phases. Explain that this is an educational simulation and that scientific facts must be sourced and verified before being added. Add a concise contribution guideline describing where world code, data models, assets, systems, and UI belong. Include a statement that NASA naming, mission information, images, and factual content must not be fabricated. Keep the documentation professional enough that another student team or mentor can understand the project without reading every source file.

Set up automated quality checks in the repository. At minimum, the project should have scripts for development, production build, linting, and type-checking. Add a lightweight test strategy and at least a few foundational tests for deterministic, non-WebGL logic such as session validation, world configuration validation, action normalization, or simulation-time calculations. Do not create meaningless snapshot tests simply to increase test counts. Browser/WebGL integration tests can be introduced later. The goal of Phase 01 is to ensure that the architecture can be changed confidently.

Keep code style consistent and production-oriented. Components should be reasonably sized. Avoid gigantic files, deeply nested conditional rendering, duplicated constants, duplicated configuration, and direct DOM manipulation unless a browser API truly requires it. Use reusable hooks only when their lifecycle semantics are clear. Keep render-heavy logic out of components that do not need to rerender. Use memoization and refs only when they solve a real performance issue; do not cargo-cult optimization everywhere. Do not install libraries merely to perform trivial tasks that can be implemented safely with platform APIs.

The initial visual scene should communicate the intended direction immediately: an elegant dark space environment, visible Sun, Earth, Moon, and Mars, subtle stars, restrained motion, and a premium simulation framing. It is acceptable for the first world objects to be simplified in geometry, but they must be real 3D entities with correct separation and transform state. Create enough polish that the first screen feels like the foundation of a professional space-exploration product rather than a bare starter template. At the same time, do not spend Phase 01 on final Moon terrain, final Mars terrain, final astronaut character, final NASA artifact models, or final cinematic storytelling. Those are later phases. This phase exists to make those later phases safe to build.

Use code comments strategically. Explain non-obvious architectural decisions, especially around client/server boundaries, simulation scaling, render-loop strategy, state partitioning, asset loading, and future extension points. Do not write comments that simply restate obvious code. Prefer expressive names and concise documentation. Add a small architecture document if the codebase benefits from it, but avoid duplicating the same information across many files.

At the end of Phase 01, the repository must contain a genuinely runnable project rather than only documentation. A clean install followed by the documented development command must launch the application. A production build command must complete without TypeScript or lint errors. The initial route must load without hydration errors. The WebGL scene must mount correctly in a client-only context. Earth, Moon, Mars, and Sun must exist as identifiable entities in the scene. The simulation clock must advance smoothly. The core stores and typed domain models must compile. The session validator must work for valid and invalid name/email values. Missing or unsupported WebGL must fail gracefully. The page must respond correctly to resizing. No secrets, local absolute paths, generated cache files, or machine-specific artifacts should be committed.

Do not prematurely build fake implementations of future features. For example, do not add a “Start Journey” button that only changes text, do not add a “NASA Artifact” card filled with invented content, do not create a fake loading bar unrelated to actual asset loading, and do not create a cinematic transition that merely fades the screen without a destination state. Every Phase 01 feature must either work or clearly represent a typed extension point for a later phase. The code should make it obvious which functionality is complete and which functionality is intentionally reserved.

Finally, inspect the resulting project as if you were an external technical mentor reviewing a NASA Space Apps submission. Confirm that the architecture is understandable, the application launches, the WebGL scene is real, the UI is not a generic template, the code does not rely on hidden local machine state, and the future Moon/Mars NASA artifact storytelling experience can be added without architectural surgery. Once all of those conditions are satisfied, commit the complete Phase 01 foundation to the repository with a clear message such as `feat: bootstrap NASA virtual simulation foundation`. The repository should be left in a clean, reproducible state ready for Phase 02, where the cinematic entry experience and name/email session flow will be built on top of this foundation.
