# NASA Virtual Simulation — Phase 02 Master Implementation Prompt

You are now implementing **Phase 02** of the NASA Virtual Simulation project. Phase 01 established the repository foundation, architectural boundaries, typed domain models, client/server separation, simulation runtime, world/entity abstractions, state domains, session service abstraction, interaction contracts, transition contracts, responsive shell, quality tooling, and the first real WebGL simulation mount. Phase 02 must build directly on that foundation and must not replace it with a separate mini-application, separate routing system, or temporary authentication flow. Before changing anything, inspect the current repository and verify that Phase 01 is actually present and functioning. Read the current architecture, identify the existing app entry point, simulation mount, state store, session abstraction, world state, transition abstraction, styling system, and test/build scripts. Preserve all healthy existing work. Do not rewrite the project merely to make the opening screen easier. If a Phase 01 architectural weakness blocks this phase, make the smallest safe architectural correction, document it, test it, and continue. Phase 02 is successful only when the project still builds cleanly and the opening experience now feels like the entrance to a professional interactive scientific exploration simulator rather than a website with a login form.

The core objective of this phase is to create a **cinematic opening experience** that introduces the user to the simulation, asks only for Name and Email, validates and stores that identity locally through the existing session service abstraction, and then transitions the same application into the initial planetary simulation without a hard page refresh or abrupt route change. The user should feel that they are entering a digital spacecraft or scientific exploration system. The first moments matter enormously. The screen should communicate scale, mystery, science, technology, and exploration before the user even interacts. The experience should begin in deep space with subtle stars, faint depth layers, extremely restrained particle movement, distant atmospheric light, subtle volumetric-looking illumination, a dark cinematic background, and a carefully controlled camera perspective. The scene must never feel like a gaming lobby, crypto landing page, SaaS login screen, or generic black screen with a centered form. The identity interface must appear to belong to the same universe as the 3D simulation. The form should be compact, refined, highly readable, and visually subordinate to the environment while still being unmistakably interactive.

Build this opening as a real application state, not as a marketing page. Introduce a dedicated entry state such as `INTRO` or `IDENTITY` within the existing state architecture, with explicit lifecycle states that can later be extended into onboarding, simulation, loading, transition, and returning-user states. Do not create a disconnected route that bypasses the simulation state. The application should have a clear conceptual sequence such as `BOOT → INTRO → IDENTITY → VALIDATING → ENTERING_SIMULATION → SIMULATION_READY`. Implement the states in the existing application state architecture or the closest equivalent already established in Phase 01. The state machine must avoid contradictory combinations such as “form submitting” while the application is already in simulation. State transitions must be deterministic and testable. A future backend authentication provider must be able to replace the local persistence layer without changing the visual components or the overall experience state model.

When the application initially loads, create a short but polished boot sequence. The boot sequence must be genuine and tied to application readiness rather than being an arbitrary fake three-second delay. Show only as much loading as the browser actually needs. The experience can begin with a subtle starfield fade-in, a quiet system-status cue, and a minimal scientific initialization treatment while core fonts, the simulation canvas, and critical assets become ready. If assets are already available instantly, do not force the user to sit through a meaningless artificial loading screen. The transition from boot to intro should be driven by readiness signals. Provide a graceful fallback if WebGL initialization fails, and ensure that the identity interface remains understandable even if the 3D background is unavailable. The user must never be trapped inside an infinite loader because one optional asset failed.

The deep-space visual environment should be carefully designed rather than filled with excessive effects. Create layered depth using multiple star fields or particle layers with different sizes, velocities, opacities, and depths so the user perceives motion through space. Use very subtle movement to prevent visual fatigue. The camera should have a cinematic starting position with a broad field of view and restrained depth. Introduce distant points of light, faint atmospheric haze, and carefully controlled gradients. If using post-processing, select only effects that improve the perception of depth and illumination, such as very restrained bloom, subtle vignette, color grading, or depth-based atmosphere. Do not stack post-processing filters because they look “advanced.” The visual hierarchy should remain clean. The center of attention should eventually move naturally toward the identity interface and then toward the simulation world. Avoid bright neon colors, excessive lens flares, giant sci-fi typography, and unnecessary HUD graphics. The tone should be sophisticated, scientific, cinematic, and credible.

The identity screen should ask for exactly two user inputs: **Name** and **Email**. Do not add password, phone number, age, address, gender, institution, company, or any unnecessary profile questions. This is an educational challenge experience. The form should have clear labels and placeholders, but placeholders must not replace accessible labels. Name validation should reject empty or clearly invalid input while still allowing normal names with spaces, hyphens, apostrophes, and common Unicode characters. Email validation should catch obviously malformed values without being unnecessarily strict. Do not write a custom email parser that rejects legitimate addresses. Trim surrounding whitespace, normalize the stored email appropriately, and preserve the user’s intended display name. Avoid storing anything except the minimum identity information needed by the simulation. Do not send the data to an external server in this phase. Do not add analytics that secretly transmits the user’s email. Local persistence must remain local.

Use the Phase 01 session service abstraction for persistence. The UI should never write directly to localStorage from a random component. Instead, create or extend a typed session repository/service with methods such as `getSession`, `createSession`, `clearSession`, and `hasValidSession`. The service should validate parsed data before returning it. If stored data is corrupted, outdated, or structurally invalid, safely discard or ignore it and return a clean unauthenticated state. Use a version field in the persisted session payload so future schema migrations are possible. Treat localStorage availability as unreliable: handle private browsing restrictions, disabled storage, serialization errors, and malformed values gracefully. A failed persistence write should not produce an unhandled exception or leave the UI half-submitted. The user should still be able to enter the experience for the current browser session using in-memory state when local persistence is unavailable.

Create a polished form interaction system. Inputs should respond immediately to focus, hover, keyboard, validation, and submission states. Use restrained motion: subtle focus glow, border/opacity changes, gentle slide or scale feedback, and a clear submit affordance. Avoid bouncing inputs or exaggerated UI animation. The user should always understand where focus is. Error messages should be concise and placed near the relevant field. Do not expose raw validation-library error dumps. The submit action should be disabled only when appropriate; avoid disabling the button so aggressively that users cannot understand why it is unavailable. Support Enter-to-submit from both fields. Preserve keyboard accessibility. The form must work without a mouse. Make the focus indicators visible against the space background. The form should still look premium when browser autofill is active.

Design the primary action as the beginning of an exploration rather than a generic “Login” button. The exact copy can be determined by the visual system, but it should communicate entry into the mission or simulation, for example “Begin Exploration,” “Enter Simulation,” or an equivalent scientifically appropriate phrase. Do not use gimmicky copy such as “Launch Yourself Into Space.” When the user presses the primary action and validation succeeds, transition the application into an explicit entering state. The button should provide immediate feedback, but it must not become a generic spinner. A subtle status change, visual lock-in, and environmental response are better. Avoid a page reload.

The cinematic transition after successful identity submission is one of the most important features of Phase 02. Do not simply fade to black and show the simulation. The existing WebGL scene should become part of the transition. The environment should visually react to the successful entry. For example, the starfield can gradually accelerate, the camera can begin a controlled forward movement, distant light can intensify, the visual center can shift, and the simulation layer can progressively reveal the Earth/Sun/Moon/Mars environment. The identity interface can dissolve, scale, move, or fade according to the camera's motion. The result should feel like the user has crossed from the introduction chamber into the actual exploration environment. The transition must be implemented as a real stateful cinematic system and should be interrupt-safe. Do not allow a double click or repeated Enter key to trigger multiple simultaneous transitions.

The transition should use the existing Phase 01 transition abstraction. Extend it instead of bypassing it. Define a semantic transition type for the entry sequence, such as `INTRO_TO_SIMULATION`, with explicit lifecycle stages such as preparing, animating, activating, and completed. The simulation destination should be the actual Phase 01 world state, not a fake landing screen. The transition should coordinate UI animation, camera movement, environment animation, and world-state activation. Keep the system deterministic enough to test. The exact visual choreography is up to implementation, but the handoff must be smooth: the user should never see the WebGL canvas disappear, remount unexpectedly, flash white, reset camera state, or visibly load a second unrelated scene. If the simulation environment needs additional assets, the transition should expose those loading requirements cleanly.

Preserve the existing simulation canvas during the identity flow whenever practical. Avoid unmounting and remounting the WebGL renderer just because the UI changes. If the simulation is already mounted in Phase 01, use that same runtime. The introductory environment and simulation environment may share the same canvas with different scene states, camera positions, lighting, visibility layers, or world activation. If a separate composition is technically necessary, build it behind the existing simulation runtime contract so it still feels like one continuous experience. The final transition should produce a stable simulation-ready state in which the same Earth, Moon, Mars, and Sun entities established in Phase 01 are available for later phases.

Create a subtle identity-presence element after successful entry. The simulation should know which user has entered, but this information should remain understated. The user’s name can be used later in the UI or onboarding, but Phase 02 should not plaster the name across the screen. Store the session in a typed domain object and expose it to the simulation layer through the established state architecture. Avoid personally invasive behavior. Do not transmit the email. Do not display the full email in the 3D world. The identity is a lightweight session key for the educational experience.

Support returning users elegantly. On application load, after validating the locally persisted session through the session service, determine whether a valid session already exists. If one exists, do not automatically create a confusing duplicate identity form. The experience can show a brief personalized “Welcome back” state or a quiet continuation entry point, but it should remain cinematic and concise. Give the user an explicit way to continue or start fresh. If the session is missing or invalid, return to the clean identity flow. The implementation should distinguish between a first-time user and a returning user without introducing unnecessary account-management UI. The future architecture should allow a backend session to replace local storage without changing this behavior.

Add a safe and simple “Reset Session” or equivalent development-facing mechanism only where appropriate. Do not expose a conspicuous logout control during the cinematic introduction unless the application design requires it. Instead, provide a developer-accessible reset during development, or a minimal account reset path that can be surfaced later. Do not make the first screen look like a profile-management system. The challenge experience should get the user into exploration quickly.

Make the visual system responsive across desktop, tablet, and mobile while respecting the 3D experience. On wide desktop screens, the cinematic intro should have strong spatial composition and enough negative space around the form. On smaller screens, the form should remain readable and not be forced into a narrow centered card over a visually busy background. Recompose the layout responsively. Preserve touch-safe controls and safe-area insets. Make sure the keyboard on mobile does not completely obscure the form. Use dynamic viewport sizing carefully. Do not lock the orientation. The intro should remain usable in portrait mode, and the 3D background should gracefully simplify if the device has limited graphics capability.

Build reduced-motion behavior into the entire intro sequence. When the user has prefers-reduced-motion enabled, shorten or simplify camera travel, particle movement, UI transitions, and scale animations. Do not remove critical context or interaction feedback. The reduced-motion variant should still feel intentional and premium, simply less kinetic. Make sure the application does not depend on animation completion events alone in a way that could leave the user stuck if animations are reduced, disabled, or interrupted.

Create an explicit visual layering model. Separate the WebGL layer, cinematic overlay layer, identity interface layer, accessibility layer, and transient notification/status layer. Define clear z-index and pointer-events behavior. The 3D background should remain visually continuous underneath the form. The form should receive pointer events; purely decorative overlays should not block clicks. Avoid uncontrolled absolute-positioned elements scattered throughout the codebase. Create a reusable composition/container for the opening scene. This will make it easier to add future onboarding, system-status indicators, and story elements.

Add a subtle “system identity” treatment to establish the simulation’s brand without turning it into a fake military interface. A small project identity, mission title, or scientific expedition label can appear tastefully. The challenge name can be acknowledged, but do not overwhelm the user with competition branding. The focus should remain on the experience. Typography should prioritize readability and scientific confidence. Use a restrained type scale, careful letter spacing, and consistent weights. Avoid novelty fonts that harm readability. Do not use huge all-caps text everywhere.

Create a meaningful first-time user micro-onboarding around the transition. After the user enters the simulation, the initial environment can briefly communicate something like “Earth,” “System online,” or another concise context cue, then settle into the actual exploration environment. Do not dump movement instructions or all future controls into Phase 02. Controls and astronaut movement will be handled later. The purpose here is to make the first entry feel finished, not to overload the user. A small initial context cue can be implemented as a future-ready UI component that later phases can reuse.

The animation system must be robust. Use requestAnimationFrame-driven or renderer-driven timing for 3D movement, and use an animation library only when it meaningfully improves orchestration. Do not build core 3D camera movement on arbitrary CSS timers. Synchronize UI and 3D transitions through a small transition coordinator or state machine. Ensure cleanup on unmount, route replacement, and aborted transitions. If the user resizes the window during the entry cinematic, the system should adapt rather than break. If a browser tab becomes backgrounded, timing should remain stable. Use elapsed/delta time rather than assuming a constant frame rate.

The starfield and atmosphere should be performance-conscious. Do not generate thousands of React elements for particles. Use GPU-friendly instancing, buffers, or a dedicated particle approach. Keep particle density adaptive to device capability where appropriate. The intro must remain visually impressive on a normal laptop without forcing extreme GPU usage. Monitor render cost. Cap DPR. Avoid expensive real-time effects until there is evidence they are needed. Create a reduced-quality rendering path for lower-end devices, such as lower particle density, simplified post-processing, reduced shadow quality, or less intensive environment effects. Do not detect performance using fragile browser heuristics; prefer conservative defaults and a small number of controlled quality tiers.
